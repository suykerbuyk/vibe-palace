# vibe-palace v10.2.0 — install-on-every-host runbook

This runbook installs v10.2.0 on every host that writes a vault, and verifies it,
**before** the authored-only migration and the quantum split. It does **not**
migrate any vault and it does **not** run the live migration: those belong to
`live-migration-run-on-the-personal-and-quantum-vaults` (the next step after this
rollout), which is built on the verified inventory below.

For *what* changed in v10.2.0 — the contract changes, surface bump and the
authored-only / host-local-index work — read the release notes,
[`v10.2.0-release-notes.md`](v10.2.0-release-notes.md). This page does not repeat
them.

## Why an inventory, and why an attestation

Nothing can verify a host's binary version remotely. `vp check --check
writer-identity` records `sha256(hostname + vaultPath)[:8]` fingerprints counted
from session-note filenames (`internal/check/writer_identity.go:25`, `:51-67`); it
reports *who has written*, not *what version they run*, and a retired host stays in
that list for as long as its notes exist. So the rollout is driven by an explicit
**per-vault inventory** of hosts, each row carried from **installed** to
**verified** (or marked **retired**), and the migration's operator attestation is
built from the verified rows. That attestation — "every writer host has synced,
pushed, been left clean, and runs v10.2.0 or later" — is exactly the fact no code
can check.

**The subset check.** For each vault, every fingerprint that `vp check --check
writer-identity` reports on a host must appear in that vault's inventory table
below, in any state. Retired rows keep that check true for hosts that no longer
write, without installing anything on them.

## Per-host install and verify

Do this on **every non-retired row** of both inventory tables. For a quantum-vault
row, be on the VPN / Teleport first (see Access).

1. **Install v10.2.0.** Either unpack the release archive from the v10.2.0 GitHub
   release, or `make install` from a source checkout at the release commit.
2. **Restart every AI harness on the host.** A running MCP server resolved its
   vault and surface at startup; it must be restarted to pick up v10.2.0.
3. **Verify, all three:**
   - `vp version` — reports `v10.2.0`;
   - `vp check --check stale-mcp` — passes (no running server on an older surface);
   - `vp check --check release-version` — passes (the binary's tag matches
     `MCPSurfaceVersion.RequiredDataFormat`, i.e. `10.2`;
     `internal/check/release_version.go:52`).
4. **Confirm the fingerprint.** Run `vp check --check writer-identity` against the
   vault on this host and confirm the reported fingerprint matches this host's row
   (for the quantum vault, write the fingerprint into the TBD cell).
5. **Sync and push until clean:** `vp vault sync`, then push, repeating until the
   vault is clean and all remotes are at the pushed tip.
6. **Set the row to verified, with today's date.**

A host is **verified** once steps 1–6 hold. The per-host `vp index rebuild` step
below is **separate** and is **not** required for the verified state.

## The per-host index rebuild (run once per vault — NOT part of "verified")

Under the host-local-index design, each host compiles its own search index and
clears its historical backlog with one `vp index rebuild` per vault. This runbook
records the step; it is **sequenced by `live-migration-run-on-the-personal-and-quantum-vaults`
after the live run**, not gated by this rollout's verified state. L's host check
expects coverage `partial`, with a backlog, until a host has run it. Its locks are
host-local under `palace/.local/locks/` in each vault, so one host's run never
blocks another host's.

### Personal vault — the quantum exclusion

Until the quantum projects are split into their own vault, the per-host rebuild on
the personal vault **must leave out both `qa-metabuild-system` and `orchestrator`**
(operator ruling 439). Run exactly:

```
vp index rebuild --all --skip qa-metabuild-system --skip orchestrator
```

The run's output **must name exactly the personal-vault project list** — every
project except the two quantum ones, i.e. these 26:

```
atlassian-vault  cando-rs      dotfiles        filecoin-gateway  go-proxmox
grok-build       hal9k-dbg     hnsw            learn-claude-code mandelbulb
mlnx-sw-os       modo-melius   obsakkadscale   obsjohnsvault     obsmettleops
proteus-rs       pveforge      recmeet         recmeet-v1        rezbldr
rezbldrvault     rusty-can     tools           vibe-palace       vibe-vault
vp-pitch
```

If the output names `qa-metabuild-system` or `orchestrator`, **stop**: the `--skip`
flags were dropped, and the rebuild would embed a quantum project before the split.
Never run `vp index rebuild` on the personal vault without both `--skip` flags (or
without an explicit personal-vault project list). `qa-metabuild-system` and
`orchestrator` keep their backlog and read `partial` until the post-split rebuild in
the quantum vault (`split-quantum-projects-into-their-own-vault`).

### Quantum vault

The two quantum projects are rebuilt once, **in the quantum vault**, after the
split — not here, and not on the personal vault.

### Standing rule: no quantum search before the split

**Do not run `vp_search`, `vp search` or `vp_search_cross_project` in any way that
can reach `qa-metabuild-system` or `orchestrator`, on any host or on any copy,
before the split** (operator ruling 439). This includes cold searches that would
trigger an index build of those projects. The per-host rebuild above is the only
sanctioned index work that touches the personal vault before the split, and it
skips both quantum projects.

## Hand-off

- When every non-retired row in both tables reads **verified** with a date, and
  every retired row carries its reason, the inventory is complete and the
  writer-identity subset check holds for each vault.
- The Chair holds these verified rows. They are the operator attestation's source
  for `live-migration-run-on-the-personal-and-quantum-vaults`, which is the **next
  step** and whose first precondition is this verified inventory. Nothing verifies a
  host's version remotely, which is why the attestation — and this runbook — exist.

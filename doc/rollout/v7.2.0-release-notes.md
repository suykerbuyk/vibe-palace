# vibe-palace v7.2.0 — release notes

Released 2026-09-21. Task `move-per-project-config-out-of-the-shared-vault`,
release R4.

## The headline: per-project config leaves the shared vault

Per-project configuration is host-local. It describes one machine's view of
one project, and the vault is shared across machines, so an override written
into the vault on one host became every host's setting. Rewriting it was also
a vault-history change that blocked history sync for everything else.

As of v7.2.0 the vault's `Projects/<slug>/config.toml` is **retired**:

- **Nothing reads it.** `vp` no longer decodes it for any setting.
- **Nothing writes it.** `vp init`, `vp config sync`, `vp migrate` and
  `vp config upgrade` no longer create or upgrade it, and the vault file tools
  (`vp vault write` / `vp_vault_write` and their siblings) refuse to create it.
- **`vp check --check vault-project-config`** lists any that survive on disk,
  committed or not, with the command that removes each one.
- **Split and merge** (`vp_vault_split`, `vp_vault_merge`) no longer carry it.

The one per-project tier that remains is the host-local file
`<config dir>/vibe-palace/projects/<slug>.toml` (on Linux,
`~/.config/vibe-palace/projects/<slug>.toml`). It carries
`palace.scoring.min_score` and `palace.scoring.rooms.<room>.{high,medium,low}`
only, and it is what `vp tune rooms --apply` and `vp discover rooms --apply`
write. `vp status` names it when a project has one.

## Removed: the per-project tier for seven config sections

These sections could be overridden per project in the vault file. They are now
**host-level only** (`~/.config/vibe-palace/config.toml`):

- `[palace.rooms]`
- `[search]`
- `[chunker]`
- `[palace.llm]`
- `[archive]`
- `[summarization]`
- `[enrichment]`

At the time of the change, no vault file in the maintainer's live vault used
any of them, so this is a capability removal rather than data loss. Re-check
your own vault before upgrading: any of these sections set in a
`Projects/<slug>/config.toml` stops applying at v7.2.0.

## Behaviour changes

- **A project whose only init marker is `Projects/<slug>/config.toml` is no
  longer an initialised project.** This is typically a project `vp init`-ed by
  an older binary that has no sessions or tasks yet. It is not enumerated by
  `vp config sync`, `vp absorb` refuses it with a "run `vp init`" message, and
  `vp check --check vault-project-config` lists its file. **Recovery: re-run
  `vp init` in the project**, which lays down the `commands/` and `skills/`
  scaffold that marks a project as initialised.
- **`vp init` no longer writes `Projects/<slug>/config.toml` or
  `tasks/{done,cancelled}`.** The task archive directories are created on the
  first retire or cancel.
- **`vp init --vault-path NEWDIR` on a host that already has a global config**
  now creates NEWDIR as a complete vault — a git repository (subject to the
  host's `git_enabled`), the canonical `.gitignore`, the data-format stamp —
  through the same step a first install uses. Previously the directory
  appeared only as a side effect of writing the retired config into it: bare,
  unstamped and not a repository. A configured `vault_path` that has gone
  missing is still not recreated.
- **`vp init`'s project-scaffold failures are now `[FAIL]` with a non-zero
  exit.** They were `[info]` while the retired config step ran first.
- **`vp config upgrade --project SLUG` is retired and refuses.** To scaffold a
  project in the vault, run `vp config sync --tier project --project SLUG`.
- **`LoadConfig`'s `[meta]` version check** now runs on the host global config
  only. The "config has no `[meta]` block" warning that some vault project
  files produced stops.

## Version gate: every host must upgrade

v7.2.0 raises `MCPSurfaceVersion` to 7. Once any upgraded host writes to the
vault and that write is synced, an older binary refuses every mutating command
against that vault (exit 2, with the upgrade remediation). That is
deliberate: an older binary would re-create the retired file on its next
`vp config sync`, jamming its own history sync, or revive deleted overrides
through `vp tune rooms --apply`. `VP_SURFACE_GATE=warn` bypasses the gate and
is not recommended during this rollout.

## Rollout: removing the retired files

The files are inert once every host runs v7.2.0, and removing them is a
separate, deliberate step: a one-shot command,
`vp migrate project-configs [--vault PATH] [--apply]`, that reports what each
file held and, with `--apply`, deletes the tracked ones and commits the removal
as one commit. It never pushes. `--vault PATH` names a vault other than the
configured `vault_path`.

1. **Upgrade `vp` on every host** that writes to the vault. Derive the list
   with `vp check --check writer-identity`; do not work from memory.
2. **Rehearse** the whole pass on a remote-stripped copy of the real vault,
   never on the live one.
3. **Dry run on the live vault:** `vp migrate project-configs`. It deletes
   nothing. For every file it prints the `palace.scoring` block to carry into
   that host's `<config dir>/vibe-palace/projects/<slug>.toml`, rendered exactly
   as the host-local file's writer would write it, and the sections dropped
   with no per-project tier. It ends with the census of untracked files,
   `untracked survivors: <paths or none> (N on disk, M tracked)`. **Keep this
   transcript:** it is the only record of what each project's file held.
   **Resolve every untracked file the census names before applying** — commit
   it, or remove it with `vp vault delete <path>` — because `--apply` refuses
   while any untracked `Projects/*/config.toml` exists, and prints that
   `vp vault delete` command for each one.
4. **Apply, once, on one host, last,** in a maintenance window during which
   nobody works on another host: `vp migrate project-configs --apply`. It
   prints the same report, then refuses unless all of these hold:
   - no config is untracked;
   - no config "cannot be retired as found": a file that is not a regular file
     (a symlink, say) or does not decode as TOML is marked
     `CANNOT RETIRE: <problem>` in the report, and `--apply` refuses with
     `<path> cannot be retired as found (<problem>); fix or remove it, then
     re-run`, where `<problem>` is `not a regular file` or `decode: <TOML error>`;
   - the vault is the top level of its own git repository;
   - git is enabled and a commit identity is set;
   - no merge, cherry-pick, revert or rebase is in progress;
   - `Projects/` is clean;
   - `HEAD` is on a named branch;
   - a surface stamp at this binary's version is committed — in `HEAD` for a
     vault with no remotes, or at every remote's tip, each tip an ancestor of
     `HEAD`.

   It then deletes the tracked files and commits the removal as one commit. A
   refusal deletes nothing, and a failure after the first deletion restores
   every file from `HEAD`. One case is different: if the commit lands but git
   leaves some paths in it, that commit holds part of the retirement, the rest
   is restored, and the command exits 2 naming both. No data is lost, and
   re-running `--apply` finishes it.
5. **Restore any scoring you want back** by pasting that project's block from
   the transcript into `<config dir>/vibe-palace/projects/<slug>.toml` on each
   host that wants it. The block's headers are fully qualified, so it stands
   alone as valid TOML.
6. **Push the deletion commit** — `--apply` commits but never pushes — then
   verify it on the live remote by content, not by comparing a commit SHA.

**The one residual the gate does not close:** a host that runs
`vp tune rooms --apply` after the deletion but before it has pulled the raised
stamp commits a change to a file the deletion removed, and its next pull is a
modify/delete conflict. The mitigation is the maintenance window itself.

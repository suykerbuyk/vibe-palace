# ADR 016: The Index-Building Embed Pass Is a Host-Local Singleton per (Host, Vault)

**Status:** Accepted (2026-10-14)
**Deciders:** Project owner
**Context:** Epic `host-local-hnsw-index-rebuilt-from-vault-artifacts` — this ADR extends ADR-014's
index run lock to cover the engine paths that bypass it today. Grounded in the source-grounding scope
(vp-imp1, 2026-10-14) and in the ADR draft's two adversarial-review rounds (vp-adv-grok) with the
Chair's rulings and the operator's approval. It builds on **ADR-014** (the search index is per-host
derived data compiled from vault artifacts; its decision 7, "Two locks") and affects the open children
`ingester-budget-placeholder-multiplexed-host-stays-hot`,
`converter-close-waits-on-an-uncancellable-hnsw-build`, and
`search-cold-index-detached-background-build`. The implementation breakdown lives in the task, not in
this ADR.

## Context

ADR-014 made the search index per-host derived data and built the index **run lock** — one per (host, vault), non-blocking, held for a whole ingest or rebuild run: `indexstore.TryRunLock` (`internal/indexstore/runlock.go:75`) over `vaultlock.TryAcquireFile(vault.IndexRunLockPath())` (`runlock.go:106-108`; path `palace/.local/locks/index-run.lock`, `internal/storage/paths.go:243-245`). The ledger-driven triggers reach it two ways, not one: the SessionEnd/PreCompact hook (`internal/hook/hook.go:397`), hook-less capture (`internal/tools/session_tools.go:661`), a pull (`internal/storage/ingest_trigger.go:110`) and `vp mcp` startup (`cmd/vp/cmd_mcp.go:123`) each spawn a detached `vp drain archives` that converges on `ingest.Run` (`internal/ingest/run.go:180`); whereas `vp index rebuild` calls `ingest.Rebuild` **in-process** (`cmd/vp/cmd_index_rebuild.go:157`), and `vp_refresh_index` spawns a detached `vp index rebuild` (`internal/tools/system_tools.go:953`, launch at `:1003`), **not** `drain archives`. `ingest.Rebuild` try-locks (`indexstore.KindRebuild`) and then calls `Engine.RebuildExplicit`/`RebuildNoEmbed` **while still holding the run lock** (`internal/ingest/rebuild.go:76`,`:256-264`) — the `RunHeld` pattern, since "a second try-lock on a new descriptor would fail on Linux" (`rebuild.go:226-229`). A trigger that loses the lock records its archive in the project inbox (`indexstore.NoteFirst`, `internal/indexstore/inbox.go:35`) and exits. So the **ingest/rebuild pass is already a singleton**: at most one per vault.

The redundancy is elsewhere. Each `vp mcp` process builds its own `*search.Engine` (`internal/search/engine.go:172`) with its own in-flight-build map `buildsRun` (`engine.go:190`), its own loaded embedder, and — under `WithBackgroundConverter` (`engine.go:155-160`, MCP-only) — its own converter goroutines. Two engine paths produce an index-building embed pass with **no production engine path taking `TryRunLock`** (confirmed: no non-test caller in `internal/search`; `tiers_test.go:407`,`:597` are tests):

- **cold/stale `vp_search`** → `Engine.Search` (`engine.go:532`) → `ensureIndex` (`engine.go:338`) → `rebuildAndRemember`/`rebuild` (`engine.go:1149`,`:1231`), whose build embed is `embedMisses` → `EmbedBatch` (`engine.go:2447`,`:2465`, reached only from `rebuild` at `:1495`);
- **the brute→HNSW converter** → `maybeStartConvert` (`engine.go:1718`) → `runConvert` (`engine.go:1915`), which builds off the engine locks and takes only the per-project commit lock (`:1921`,`:2035`).

(Proactive warm-up `Engine.WarmEmbedder` (`engine.go:246`) calls only `embedder.Dimensions` (`engine.go:260`) and does **not** build an index or feed `ensureIndex`; a cold `Search` separately waits ≤`readyWait` (15s) for model construct before `ensureIndex`, `engine.go:572`,`:579`. Both stay per-process.)

Each such pass takes only its own per-project commit lock, so N `vp mcp` instances on one host can embed the same project's corpus concurrently. On a multiplexed Herdr host this keeps the machine ~2×(4–5 cores) hot and is the code half of the operator's "very slow and resource intensive" observation (`ingester-budget-placeholder-multiplexed-host-stays-hot`). The holder record (`Holder` PID/kind/start_time, `runlock.go:43-49`) is advisory — "only a try-lock is authoritative" (`runlock.go:37-42`) — read for the bootstrap `index_coverage_detail.run` field via `coverage.go:153`; it is never read to decide lock *ownership*, though it IS read to coordinate: `vp_refresh_index` refuses while it names a live pid (`system_tools.go:996`) and lifecycle checks `h.Kind == KindLifecycle` (`internal/indexstore/lifecycle.go:314`).

## Decision

1. **Reuse the run lock; extend its coverage — do not add a primitive, and never try-lock inside the engine build.** One lock, one invariant: at most one corpus-building embed pass per (host, vault). The **only** process that acquires the run lock to build a corpus is the detached `vp drain archives` / `vp index rebuild` process, which holds the lock across `RebuildExplicit`/`RebuildNoEmbed` via the existing **`RunHeld` pattern** — the holder passes its `*RunLock` in rather than opening the lock file a second time, "which would fail on Linux" (`rebuild.go:226-229`). No `internal/search` engine path try-locks: a corpus build inside an MCP engine would open a lock its own process may already hold (self-conflict), and would invert the package's documented order (`internal/search/lock.go:20-39`: project mutex → commit lock → `e.mu`; the commit lock is a leaf and is "never the index run lock"; the run lock is taken *before* any commit lock, never while one is held). The cold-search and converter paths therefore respect the lock without taking it in the build body (decisions 3, 4).

2. **Embed-to-BUILD is the singleton; embed-the-QUERY, model warm-up, and loading a prebuilt index stay per-process.** Each `vp mcp` keeps its own loaded embedder and embeds its own queries (`searchReady` → `embedder.Embed`, `engine.go:649`) with no lock — a query must never wait on an index build. The per-process `readyWait` model-load wait in `Search` (≤15s, `engine.go:572`) stays and is **not** the singleton. What takes the run lock is specifically the **corpus build embed** — `rebuild` → `embedMisses`/`EmbedBatch` (`engine.go:1495`,`:2447`,`:2465`) and the converter — never `searchReady`/`SearchReady`'s query embed. **Loading an already-built index from disk is neither embed nor build and is explicitly allowed off-lock** — `newHNSWIndexFromDisk` / chunk-store read (`internal/search/hnsw_persist.go:485`); this is the consume step decision 4 relies on. `IndexDrawers` — the capture-path embed that may construct a brute index (`engine.go:823`, `lockProject` at `:855`) — is **intentionally outside** the singleton: it is a per-capture insert, not a corpus rebuild, and already short and commit-locked.

3. **The brute→HNSW converter stays in the MCP engine but runs under the run lock, one per vault, and only for in-session promotion.** The in-memory kind swap is MCP-only (`WithBackgroundConverter`, `engine.go:155-160`: no CLI or detached-ingester process runs it), so the converter cannot move to the detached drain — that process has no `convertEnabled` and cannot do the in-memory swap. Under this ADR, the in-MCP `runConvert` path handles **only** in-session promotion of a brute index that a live engine grew via capture inserts (`IndexDrawers`, itself outside the singleton, `engine.go:823`,`:907-920`). A cold or first large build does **not** go brute-then-convert in an MCP engine — the detached `vp index rebuild` builds HNSW directly (`RebuildExplicit` → `selectKind(converts=true)` → `kindHNSW`, `engine.go:1121`, `hnsw_index.go:162`). So `maybeStartConvert`'s no-op on a cold engine is **CORRECT, not stranded** — `e.mu.RLock(); b, ok := e.indexes[project].(*bruteIndex); … if !ok || b.Len() < hnswSelectT { return }` (`engine.go:1723-1727`): no in-memory `*bruteIndex` ⇒ return — an implementer must not "fix" it.

   `runConvert` (`engine.go:1915`) acquires the run lock (via `TryRunLock`, as a transient non-holder-becoming-holder for this process, which holds no run lock otherwise) **before** `lockProject` (`:1921`), keeping the documented order (decision 1) and guaranteeing one convert per vault. A declined converter (`TryRunLock` returns `ok=false`) simply **backs off and re-fires on the next `maybeStartConvert` trigger** (the existing write-counted `convertBackoff`, `engine.go:1735`) — it writes **no** inbox marker, so the rebuild holder never has to recognize or clear a token it did not serve. `Engine.Close` (`engine.go:2517`) still waits only on a converter **this** engine started (`convertWG`, `:2525-2528`); a separable follow-on threading `context` into `hnswIndex.Build` (`internal/search/hnsw_index.go:446`, no ctx today) bounds that wait.

4. **A cold search never builds inline; it serves degraded, coalesces, and ensures the detached pass is running.** Because no engine path acquires the run lock (decision 1), a cold/stale search in **any** process — before it would reach `lockProject` — returns the cheaply-available answer now (notes-only / the in-memory index as-is via `servableInMemory`, `engine.go:506`), records the generic "re-index wanted" (decision 5), ensures the detached singleton pass is running (spawns a `vp index rebuild` for the project — the child's own `TryRunLock` is the authority, decision 4 does not try-lock from the search path; see Consequences for the burst), and returns. The build is done only by that detached process.

   **The fuller result is consumed on a later search by a generation-WITNESSED disk LOAD, not a rebuild.** On a `Gen` change (`indexstore.ReadGeneration`, `engine.go:348`; a graph-only holder commit bumps `Gen`, not `Epoch`, `internal/indexstore/generation.go:26-27`, so the consumer keys on `Gen`) the engine loads `hnsw.idx` off-lock — `newHNSWIndexFromDisk` (`hnsw_persist.go:485`), whose `ReadGraph` is atomic-rename-safe and lock-free (`internal/indexstore/graph_read.go:15-21`) — taking **neither the commit lock nor `e.mu`**. The hazard is **not** a torn file (the atomic rename rules that out) but a graph newer or older than the chunk store it is paired with. The install is therefore gated by a witness: **read `Gen`, load, re-read `Gen`; if `Gen` OR `Epoch` moved between the two reads, do not install — retry on the next search.** This is the lock-free analogue of the epoch-recheck `saveGraph` already does under the commit lock (`hnsw_persist.go:524-529`).

   **No-graph projects stay notes-only until the detached rebuild commits.** A project that has never been built has no `hnsw.idx`: the search path never creates one (`selectKind` returns `(kindBrute, graphNone)` with "no search-path conversion", `hnsw_index.go:161-165`), and `newHNSWIndexFromDisk` returns `(nil, noGraph)` (`hnsw_persist.go:406`). For such a project the witnessed load has nothing to install, so the degraded answer **remains notes-only** until the detached `vp index rebuild` (which embeds local misses in `modeExplicit`, `engine.go:1121`) commits a servable store; this is the honest cold-start UX of serve-degraded, not a new in-engine build path.

5. **The coalesce record extends the inbox idiom, but every reader is taught the new token — it is NOT reused unchanged.** `first.inbox` (`internal/indexstore/inbox.go:25`, under `index/<p>/`) today holds only archive source_sha256s; its readers drop anything that is not 64-hex (`readInbox`, `inbox.go:67`, `shaPattern`), and `NoteFirst` refuses a non-sha before it locks (`inbox.go:35`). A generic "re-index wanted" token carrying exactly **one** meaning — a corpus-rebuild want (a cold search, or a fingerprint change), served by the detached `vp index rebuild` and cleared post-generation-bump; it does **not** carry a convert request (decision 3) — is given a shape the readers are taught to pass through — a **reserved marker line** distinct from `shaPattern` (not a free-form string that could collide with a sha, and not sha-shaped since `shaPattern` is exactly 64 hex). Readers that MUST change to see it, none "reused unchanged": `readInbox` (`inbox.go:59`), `Tx.Firsts` (`inbox.go:57`), `ReadFirsts` (`inbox.go:108`), `NoteFirst`'s guard (`inbox.go:35`), and `inScopePending` (`internal/ingest/run.go:864`, the predicate `ReleaseAndRecheck` actually calls). **Clear:** a **new clear site** removes the marker only after the holder's engine rebuild commits and bumps the generation — NOT `tidyProject`'s `!listed` rule (`run.go:840-854`), which would drop a non-archive token on first visit, before the build. **Loop:** the holder puts a just-served marker into `ReleaseAndRecheck`'s `seen` set (`runlock.go:202`,`:230-238`) so it does not re-acquire on its own served want; the recheck must ignore a marker this hold already served. The archive lost-trigger guarantee (`NoteFirst`, `ReleaseAndRecheck`, `inScopePending`'s archive rescan) is reused *in structure*, but a generic token has no durable archive file, so correctness rests on the new clear site + the `seen` membership, not on the archive-rescan.

6. **An inter-run cooldown lives in the run-lock acquire path — but the coalesce marker is persisted first.** A trigger that fires within a cooldown of the last completed run for that (host, vault) defers rather than starting another back-to-back pass, so a multiplexed host does not stay continuously hot. The deferral is **in the caller, not buried inside `TryRunLock`**: a cooldown is "do not try," which is not `ok=false`, so putting it ahead of the flock in `TryRunLock` (`runlock.go:75`, which today only try-locks and writes the holder, `:89-101`) would drop a cold-search want that had no archive file. The caller therefore writes the decision-5 marker **first**, then consults the cooldown and returns. This ADR fixes the *mechanism* (a last-completed marker beside the holder record, consulted on acquire); the *number* is set by the Scope-6 budget measurement, never a guessed constant. **RunKind:** the corpus build runs as the existing `KindRebuild` — the detached builder is literally `vp index rebuild` (already `KindRebuild`), and the converter's transient acquire reuses `KindRebuild` too — so the enum (`runlock.go:76-79`, which rejects any other kind) does NOT grow and the user-visible `h.Kind` surfaces (`coverage.go:164`, `system_tools.go:997`) are unchanged.

7. **No new PID-liveness takeover logic.** The advisory flock is released automatically by the OS on process exit, "so a lingering .lock marker file left behind by a crash is harmless: the next Acquire reopens it and locks cleanly" (`internal/vaultlock/vaultlock.go:15-17`). That already delivers stale-takeover on a dead or crashed holder. The holder PID+start_time record stays advisory telemetry; nothing reads it to decide lock ownership.

## Consequences

**What changes:** no engine path builds a corpus inline — the cold-search path degrades + coalesces and ensures a detached `vp index rebuild`; the converter acquires the run lock in `runConvert` before `lockProject`; the inbox gains a generic marker with a new post-generation-bump clear site; the acquire path consults a cooldown marker after the caller persists the want. A consumer warm-starts from disk on a `Gen` change, installing only behind a `Gen`/`Epoch` re-read witness (no-graph projects stay notes-only).

**What stays:** the run lock, `vaultlock`, baseline/ledger, the per-project commit lock, `Engine.Close`'s `convertWG` wait (now only on a converter this engine started), and per-process query embedding / model warm-up are unchanged in contract. ADR-014's "one path per project, selected by size" and EfSearch-in-fingerprint are untouched. Bootstrap's `SearchReady` (`engine.go:612`, never builds) is unaffected. (`NoteFirst`/`readInbox`/`ReleaseAndRecheck` are reused in *structure* but edited for the generic token — decision 5.)

**Named consequences the operator is approving:**
- **The winning builder is the detached process, so no search goroutine blocks on a corpus embed** (decision 1/4). This preserves `be6eca2`'s no-inline-hang property on *every* process, including the one that triggered the build — unlike a design where the winning search builds inline on its own caller goroutine (`ensureIndex` owner runs `rebuildAndRemember` itself, joiners bounded by `joinBuildTimeout` 5s, `engine.go:365-400`).
- **`vp_refresh_index` can false-refuse on a recycled pid** (`system_tools.go:996` refuses while `ReadHolder` names a live pid; pid reuse is admitted at `runlock.go:40-42`) — **accepted**, because decision 7 deliberately adds no takeover. And a long singleton build makes an explicit refresh refuse with **no** coalesce record unless decision 5's marker is also written from `refreshIndexHandler` (`system_tools.go:953`), which this ADR requires. `DryRun` is unaffected (takes no lock, `system_tools.go:965-969`).
- **The startup backstop fires on every `vp mcp` start** (`cmd_mcp.go:106-128`), so the decision-6 cooldown applies to it; N servers starting together defer rather than queue, and their archives survive (durable on disk), but a generic want racing startup survives only because decision 5's marker is written first.
- **A vault-wide run lock means one held build blocks every project's cold build on a cross-project search** (`ensureAllIndexes` → `ensureIndex` per project, `engine.go:461`). On a multiplexed host a cross-project search returning a mix of warm + skipped-not-ready projects is the common case, not the rare one.
- **`Engine.Close` of the engine that WON the converter hold blocks the singleton until `Build` returns.** `Close` waits on `convertWG` (`engine.go:2525-2528`); because `runConvert` holds the vault run lock across that `Build` (decision 3), a shutting-down converter-holder keeps every other vault build out until it finishes or the build's context (the separable follow-on) fires. `TryRunLock` is non-blocking (`runlock.go:71-74`), so a would-be converter never blocks `Close`; only a converter already **inside** `Build` is awaited. **That follow-on's second half (the holder observing ctx, then calling `Release`) is therefore load-bearing, not optional** — cancelling `Build` does not by itself free the run lock.
- **A convert and a corpus rebuild are indistinguishable in telemetry.** Both hold `KindRebuild` (decision 6), so coverage (`coverage.go:164`) and `vp_refresh_index` (`system_tools.go:997`) report a convert-in-progress as "a rebuild holds the lock" — **accepted**; not a reason to grow the enum.
- **N cold searches spawn N `vp index rebuild` children; N-1 exit fast and the parent's marker is the coalesce.** With N engines cold at once, up to N children may start before any acquires; each loser's own `TryRunLock` is the authority and it exits with `ErrRunLockHeld` writing nothing (`rebuild.go:76-82`). The want is kept by the **parent's** decision-5 marker (written before return), **not** by the child's exit. The bounded spawn burst is **accepted** (an optional per-engine "already spawned" bit is tuning, not required for correctness); the search path must not try-lock to decide whether to spawn (that would reopen decision 1).

**Crash / stale-takeover:** unchanged and relied upon — OS flock release (decision 7, `vaultlock.go:15-17`; `TestRunLockLivenessIsTheOSLock`, `runlock_test.go:51-70`). A holder that dies mid-build leaves a stale advisory holder *file* (not OS-released; `Release` removes it, `runlock.go:176-184`); the next trigger try-locks cleanly and rebuilds. A partially-built index is caught by the ledger/generation completeness rules already in place (the heal and the generation witness).

**The one genuinely-new sub-mechanism:** the **generic "re-index wanted" coalesce marker** in the inbox (decision 5) — everything else extends an existing caller or seam. Its correctness hinges on the holder clearing it only after a committed, generation-bumped build, so a request is never lost and never loops.

**Risk surface:** decisions 1–4 move embed/build work across the process boundary and change who waits on whom; they touch the concurrency and search surface and need the full test gate.

## Alternatives considered
- **Pass the held `*RunLock` into the engine (the `RunHeld` pattern), rather than try-lock inside the engine build — ADOPTED** (decision 1), not a new primitive. It is the shape `ingest.Rebuild`/`RunHeld` already use so a holder does not open the lock file twice (`rebuild.go:226-229`). The rejected shape is the opposite: acquiring `TryRunLock` inside `rebuildAndRemember`/`ensureIndex`, which self-conflicts on Linux (the same process may already hold the lock) and inverts the documented order (commit-then-run instead of run-then-commit, `internal/search/lock.go:20-39`).
- **A new parallel lock for engine builds** — rejected: duplicates the flock idiom and splits the "one pass per vault" invariant across two locks that could disagree.
- **Refuse-fast cold search (keep today's `be6eca2` behavior as the end state)** — rejected: the operator chose serve-degraded + coalesce so a non-holder returns a useful answer now instead of a `vp index rebuild` hint.
- **Per-engine converter (status quo)** — rejected: it is exactly the multiplex redundancy; N engines converting one project independently is the cost being removed.
- **PID-liveness takeover of a stale holder** — rejected: the OS already releases the flock on death (`vaultlock.go:15-17`), so takeover logic would be redundant and racy.
- **A separate flag file for the coalesce marker** — rejected: the inbox already has the consume/clear seam and the lost-trigger guarantee; a parallel file would re-implement both.
